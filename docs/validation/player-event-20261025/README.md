# 播放器状态事件提交开销

## 根因和改动

`VideoPlayer.kt` 约每 400ms 请求一次播放器状态。`download_worker.rs::emit_player_session` 最终调用 `PersistentCore::emit`。原实现为数据库失败回滚而克隆整个运行态，包含任务/spec 映射和最多 4096 项事件环；但 `CoreRuntime::emit` 只发布一个事件，改变序号及事件环，不修改任务和其他运行态。

现在先构造同一序号的单个事件并提交 SQLite，成功后再发布到运行态、通知订阅者。数据库失败时不改变运行态或发送通知。沿用原事务、事件协议、刷新间隔和通知，没有新增依赖、线程、定时器或另一套提交层；普通会改变任务的命令仍保留其既有回滚逻辑。

扩展既有 `failed_commit_restores_snapshot_spec_sequence_and_notification`：检查 PlayerSession 提交失败和带 side row 的 MediaPushRequested 事务失败，任务/spec、事件环、持久化序号、side row 和通知均不泄漏。既有成功提交及重开恢复用例继续运行。

## 实际回归

release 测试程序和 Engine 均构建成功。沙盒首次测试在进入 Rust 测试前因缺少 VC 运行库退出 `-1073741515`；保留失败记录，补齐客体测试目录的 `vcruntime140.dll` 后重跑，未修改产品或断言来处理环境问题。

完整 Core：632 通过、0 失败、9 跳过；随后显式运行 curl 2 项、WinHTTP 3 项，均通过，共 637 个不同回归。默认跳过的扫描器超时、真实 FFmpeg 回收、伪装 HLS 音频解码、交互 UAC 退出码四项仍未执行，没有计为通过。测试和产品只在沙盒运行，宿主仅编译。

## 性能对照

`scripts/validation/compare_v7_player_events.py` 使用真实 Core IPC 和 SQLite 提交。10/1000 个暂停任务，每进程先请求 4100 次状态填满事件环，再连续测量 1000 次请求。旧 Engine 作为两个相同 SHA 的基线对照；每种任务规模三轮，每轮轮换执行顺序，共 18 个样本。编译及回归结束后才开始测量。每样本核对事件序号连续、任务快照不变、数据库 checkpoint 一致且没有启动播放器子进程。

旧 Engine SHA256：`e3cc84b31d4df98a30d7e66c83765a74c35122d659f647aec341cc036fd59074`。

新 Engine SHA256：`f925ca4a0f54e88437ed104016ee81c0c045e6c4edb475659d328d20ffc70fbe`。

下表各值为三轮中位数；CPU 是 1000 次请求期间 Core 进程的累计 CPU 秒，不是播放时的整机占用率。

| 10 | 同一旧程序 B | 0.432 | 0.738 | 0.187500 | 16.414 |
| 10 | 新程序 | 0.268 | 0.448 | 0.046875 | 16.109 |

本批支持保留此改动：任务数增加时，单事件发布不再承担复制全库的成本。短时间 CPU 计时存在粒度，个别样本的 0 不能解释为零占用；RSS 差异很小，不据此声称明显节省内存。测试没有实际解码，也没有比较 IDM/AB，不能外推为视频解码、所有交互或整机性能达标。
