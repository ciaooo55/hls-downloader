# 2026-10-25：对标行为与 HTTP 自动重试

## 当前证据与改动

参考 [IDM 的失效下载地址处理说明](https://www.internetdownloadmanager.com/register/new_faq/sites2_3.html)：短效链接、登录或一次性请求失效时，需要刷新下载地址。本项目已有“更新下载链接”和请求凭据更新入口，这些入口保留；不以反复请求同一个失效地址代替恢复。

检查到本项目存在两层不一致的重试判断：HTTP 分片引擎只重试临时状态（408/425/429/500/502/503/504），外层任务调度却对所有失败直接重新排队。开启失败自动重试后，401/403/404 等确定性 HTTP 错误仍会重复消耗设置的次数。本轮让外层任务复用同一个 HTTP 判断；失败诊断、手动重试、更新请求、分片保留与后续队列继续运行均不移除。非 HTTP 错误沿用原行为，未宣称所有错误分类已重做。

新增回归使用本地 HTTP 服务和真实任务调度：开启两次自动重试，分别检查 401/403/404 只执行一次任务、503 仍执行三次任务。之后的任务必须真正下载并校验成品，才能检查前一任务的最终状态与次数。等待采用既有 Core 事件通知，没有靠固定睡眠判断“不会再重试”。既有请求刷新和凭据隔离回归继续复用。

仅复用一项已有的 HTTP 状态判断，并给设置加上行为说明，没有增加依赖、常驻进程或新的配置项。这不是指定直播站点 403 的根因修复；该站点录制仍待实际闭环。

## 竞品和浏览器范围

检查 [AB Download Manager 的 MV3 拦截实现](https://github.com/amir1376/ab-download-manager-browser-integration/blob/master/src/linkgrabber/Manifest3DownloadLinkInterceptor.ts) 与[共用下载接管代码](https://github.com/amir1376/ab-download-manager-browser-integration/blob/master/src/linkgrabber/DownloadLinkInterceptor.ts)：MV3 路径明确不能直接取消响应，并依赖浏览器 downloads API 参与。它还对请求方法、资源类型和排除规则作判断。不能把“参考 AB”解释为所有请求都能在浏览器创建下载项之前接管，也不能只隐藏暂停记录便宣称已经实现。此处是官方源码阅读结论，不是本批竞品实机对照。

本项目已有的三款实测见 [2026-10-19 的同机报告](../idm-ab-20261019/README.md)：限速场景和 CPU/内存没有全面达到 IDM/AB。历史样本不支持当前源码性能已全面达标；本轮也不以少量空闲样本代替响应延迟、活动传输和播放负载。

## 执行状态

Core 测试程序与 release Engine 编译成功，桌面 JAR 构建成功。Windows 沙盒内三项定向回归实际通过（每项 1 passed / 0 failed）：上述四类 HTTP 状态与后续队列、既有链接更新后暂停续传、既有 Cookie 入库及快照隔离。503 在分片层每轮完成 5 次尝试后失败，外层任务仍按设置共执行 3 轮；401/403/404 最终任务次数为 1，手动重试入口保留。
