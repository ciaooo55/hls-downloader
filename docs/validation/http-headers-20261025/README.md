# 普通 HTTP 响应头与大小探测修复验收

本轮解决两个已定位的问题：普通 HTTP 响应头逐字节读取并反复扫描，导致大响应头占用 CPU；批量读取链接大小时生成了没有用途的响应元数据临时文件。没有增加生产依赖，也没有修改 TLS 传输、UI 或插件。

## 实现

- `http_engine.rs::http_get` 改为 4096 字节块读，仅搜索新增字节与跨块边界。保留同次读取的正文和 64 KiB 响应头限制，以及暂停、取消和超时行为。
- `download_worker.rs::harvest_page` 的纯大小探测不再设置虚假成品、控制及进度路径，复用已有的空输出路径约定，跳过响应后缀元数据写盘。实际下载不变。
- 新回归覆盖分隔符跨块边界、上限内外以及含 NUL/CRLF 的正文完整性。已有 chunked、截断、Range、HEAD 和停止回归一并运行。

## 对照方法与结果

同一沙盒、相同旧 Engine 分别记作 baseline-a/b，与候选轮换执行三轮。旧 Engine SHA-256：`f925ca4a0f54e88437ed104016ee81c0c045e6c4edb475659d328d20ffc70fbe`。回环服务器提供普通头或额外 32768 字节响应头，不支持 Range；完整下载检查 128 MiB 正文 SHA-256，并确认任务、成品及缓存删除。大小探测经真实 Core IPC 和 SQLite，每组 3 次预热、20 次测量，使用隔离临时目录。

最终 Engine 的 18 组大小探测全部通过。每组候选产生 0 个临时文件，旧版每组产生 23 个。大响应头的 20 次探测耗时中位数：旧 A/B 为 7.576/7.544 秒，候选 0.066 秒；Core CPU 为 7.422/7.344 秒和 0.016 秒。普通头为 0.091/0.087 秒和 0.063 秒，样本中有波动，不据此承诺常规网站普遍提速或零 CPU。

中间版本（仅响应头修复，SHA-256 `7b1b9647a7ced0a2b9cc1a08cf713115b875d702297fe8a665461768614e435a`）的 36 组 GET/POST 下载完整性及清理检查通过。首次大头 GET 候选耗时中位数 1.262 秒，旧 A/B 为 1.039/1.063 秒，候选单次 0.49–1.96 秒；追加 9 组复测为 0.507 秒对 1.029/1.720 秒。两次均降低该场景 CPU，但耗时存在明显波动，不能只取最好结果。原始结果以 `header-only-*` 保存，不能当作最终二进制证据。

最终 Engine 的 9 组大响应头 GET 复测全部通过，正文 SHA 和完成/删除后的缓存检查通过。三轮耗时中位数旧 A/B 为 1.132/1.133 秒，候选 1.122 秒；CPU 为 1.078/1.047 秒和 0.484 秒，RSS 均约 13.1 MiB。本次结果支持降低这一路径的 CPU 开销，不支持普遍缩短下载时间的结论。

最终 MSI 验收在收尾中，桌面包尚未替换。本报告将随验收结果更新。

## 范围与限制

这是普通 HTTP 的局部性能和临时文件验证，不代表 TLS、所有真实网站、UI、浏览器、收费字幕、投屏设备、长期负载或 IDM/AB 全面性能对等。本轮没有重新下载或运行竞品。

指定直播站点 HTTP 403、用户原始 HLS 卡死现场、历史首次安装 Engine 15 秒启动超时仍缺少根因闭环，不能声称全部功能无问题。Chromium MV3、POST/Blob 等下载接管边界也不能保证任意下载完全没有浏览器事件。

源码保留 main 和一个 worktree。本轮构建缓存仍在项目 `.tool-cache` 中；此前自动审批拒绝缓存删除（`blocked by policy`），本轮不换方法绕过。用户备份和宿主下载均保留。
