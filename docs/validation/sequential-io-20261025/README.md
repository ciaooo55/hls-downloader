# 单流下载 I/O 与 Core 连接竞争验收

## 根因和实现

单流 HTTP/POST 路径原来每次网络 `read` 都重新打开控制文件。小响应块会使控制文件读写成为高频操作；分段下载已有按时间检查的机制。单流现在沿用 50ms 检查间隔，读取错误、真正的限速等待和结束时仍检查控制。传输层的可中断网络等待保持不变。没有新增线程、依赖、配置或缓存层。

扩大到 Core 全量库回归时，首轮为 629 通过、1 失败、9 忽略。失败是已有的 `competing_pipe_clients_connect_within_their_deadline`：16 个客户端分 8 轮同时连接，`WaitNamedPipeW` 多次返回找不到文件。原客户端只处理忙碌实例，没有处理最后一个旧实例关闭、下一实例尚未创建的间隙，因而提前结束了仍有剩余期限的连接。

微软[WaitNamedPipeW 文档](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-waitnamedpipew)明确说明：没有任何实例时调用立即返回；等待成功也不预留实例。修复仅对 `ERROR_FILE_NOT_FOUND` 在原有总期限内短暂等待，忙碌实例仍使用系统等待；权限错误等立即返回，未扩大期限或空转。现有竞争回归另核对不存在的管道按 40ms 期限返回错误。

## 实际验证

Core release 库回归 630 通过、0 失败、9 忽略；另显式执行 curl 2、WinHTTP 3、真实 FFmpeg 暂停/取消 1，均通过，共 636 项。3 个未显式执行的忽略项是交互 UAC、需要专用音频夹具的字幕解码，以及由扫描器测试调用的超时辅助用例；不把忽略算作通过。curl 临时目录剩余 0。

Core、Native Host、Updater 和 Presenter 全部重建，覆盖共享 IPC 客户端的实际使用者。沙盒中 8 个真实 Native Host 同时冷启动，各收到两条正确的协议响应；只启动一个 Core，最慢首响应 167.55ms。Presenter 进程单实例检查通过，未做新的窗口实屏交互验收。

Native Host 首次验收的独立临时目录遗漏 Engine 所需的 `vcruntime140.dll`，未得到响应；清理函数在没有残留 Core 时还返回非零，遮住了原错误。夹具现在复制输入 Engine 相邻的现有运行库，并让“没有进程可清理”正常结束，真正的清理错误仍终止。补齐后通过。初次失败输出保留，不算作产品通过或修改生产逻辑的依据。

## 性能对照与限制

同一 Windows 沙盒，每次实际下载 128MiB。三轮轮换两组同一旧版 Engine（A/B）与候选的顺序，覆盖不支持 Range 的 GET（服务端每次写 4KiB/64KiB）及 POST（4KiB），共 27 个样本。每次均核对完整 SHA256、实际请求数、成品及任务缓存删除；所有样本通过。测量 Core 进程，未运行主界面/播放器，不是完整产品或公网性能，也不是新的 IDM/AB 横向测量。

下表为每组三个样本的中位数。读取/写入次数是进程 I/O 计数，包含数据库和进度文件，不能当网络包数或物理磁盘写入次数。

| GET，4KiB | 0.250 / 0.281 | 0.250 | 5255 / 5991 | 47 | 2665 / 3033 | 20012 |

重复控制读取明显减少，64KiB 响应场景 CPU 较低；4KiB GET 的候选 CPU 与基线 A 持平，不能说全部场景 CPU 改善。小块响应下，接收循环更快后出现更多小写入，这是实际代价，未隐去。两组相同基线的耗时也有明显波动，因此不认定普遍吞吐提升。没有通过加并发、减少持久化或降低功能换成绩。
