# 2026-10-29：恢复回执与重试节奏

## 问题、根因与修复

1. **恢复到失败回执时误清理浏览器下载。** 未知交接按原请求ID查询回来后，旧分支只检查是否存在交接ID，直接进入清理。新增回归实际观察到未完成项被取消、已完成项被调用 `removeFile`。现在恢复分支复用 `desktopAcceptedHandoff` 判断；明确失败、无法展示确认窗时保留浏览器文件并恢复未完成下载。桌面已接收、用户取消等既有决定保持原行为，不自动另开下载。
2. **恢复队列提前查询。** 队列保存了重试时间，后台循环却没有检查；30秒心跳会提前查询60秒后才到期的记录。现在先检查deadline，并按所有阶段最早的deadline安排下次处理。模拟时间分别核对30秒无查询、60秒第一次、120秒第二次；没有凭此宣称整体CPU或内存降低。
3. **回执查询覆盖了浏览器中的新操作。** 查询前读取暂停状态，等待回执时用户已恢复或取消下载，旧代码仍按过期快照执行取消。新增两项回归均实际观察到额外的 `cancel(42)`。恢复分支现在在清理动作前重新读取下载项；如果已经离开暂停状态，结束跟踪并尊重浏览器中的新操作。已明确移交后的常规清理路径保持不变。

## 本地文件交接与故障退避

继续修复浏览器已完成文件（含POST/Blob导入）的恢复链路：

- Host返回传输错误或空成功回执时，旧分支删除了恢复记录。新增两项回归实际读到持久列表为空；现在保留源文件、原请求ID及恢复记录，退避后用原ID恢复。
- 首次读取持久列表失败后，旧代码一直复用拒绝的Promise。新增回归实际观察到后续心跳不再恢复导入；现在读取失败会释放该Promise，允许后续重读。
- 本地导入状态检查和共享交接跟踪将错误信封当成待确认状态，反复查询。故障回归在30秒内观察到65次状态查询，修复后这30秒内只保留最初2次；失败使用60秒间隔，正常待确认状态继续及时跟踪。断线首次确认时即记录`connection_lost`，不因退避而推迟错误反馈。该结果只证明受控故障下的请求频率，不是整体CPU、内存或竞品性能结论。

新增4个不同回归场景；受影响的下载所有权文件最终36项通过，TypeScript及两浏览器构建通过。详见 `local-import-validation.json`。沙盒的 `local-import-summary.json` 单列本次构建结果；Native Host和浏览器API仍为模拟，文件存在、复制、删除与哈希在沙盒内实际操作，不冒充真实Core复制或浏览器入口验收。

沙盒首轮失败保存在 `local-import-fixture-failure.json`：虚拟时钟未等待OS线程池中的摘要完成，尚未到达交接请求就检查终态。夹具改为相同SHA-256算法的同步计算、异步返回，并增加“已经发送导入”的前置断言；没有为消除该失败修改产品摘要实现或延长产品超时。
