# HLS 字节范围超长响应修复

## 根因与改动

`fetch_bytes_range_with_transport` 先用 `read_to_end` 读取整个服务端正文，再比较 HLS/LL-HLS 所请求范围的长度。错误服务器多发数据且不结束时，会继续等待或积累正文，不能及时报告范围错误。新增回归先在旧逻辑中复现，三秒协调等待内没有收到失败结果，退出 101；修复后通过。该夹具没有复现用户原始 HLS 卡死现场，不能据此关闭原始问题。

现在先检查已知 Content-Length，并将正文读取限制为请求长度加一字节，保留正常 Content-Range 校验和暂停/取消语义。超长响应返回真实错误，不把截断数据记成成功。

HTTPS 媒体优先使用的 curl 会先下载到临时文件，单独限制后续 Vec 不能限制这一步。因此只对已知媒体范围设置内部正文上限，在既有子进程等待循环中检查解码后的临时文件，超限则结束并回收 curl，退出后再检查一次以覆盖快速完成。没有增加依赖、线程或新定时器；普通文件不设置此上限，保留服务器忽略 Range 时的完整下载回退。

这是既有约 100ms 等待循环发现超额后的中止，不是保证落盘永不超过请求长度：仍可能有在途超额。对错误服务端及时失败，也不意味着所有网络卡顿都已消失。

## 压缩兼容性

实际 curl 为 `8.21.0-IMPERSONATE`。直接使用 `--max-filesize 8 --compressed` 的探针把解码后恰好 8 字节、线上压缩长度 28 字节的合法 gzip 也拒绝，退出 63；实验结果保留在 results，没有将这一方案用于生产。

采用 `--no-buffer` 加解码文件大小检查后，真实 curl 回归验证：合法 gzip 返回 8 字节成功；解码后 9 字节的 gzip 即使快速结束也失败；chunked 多发 1 字节但不发送终止块、Content-Length 声明 64 而只发送 9 字节且不结束，均在服务端 EOF 前返回超限错误。
