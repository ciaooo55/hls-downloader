# 直播外置音轨回收的控制归属

## 根因与修复

`LiveAudioRecorder` 创建独立的 `audio.control`，但此前将主任务的 `ThrottleContext` 原样传给音轨线程。HLS 子请求从这个上下文获取网络控制文件，因此读取的是主任务 `control`。视频失败或提前退出时，音轨回收写入 `audio.control=cancel` 后等待线程退出；如果音轨请求还在等待响应，主任务控制文件仍为 `run`，取消就无法到达网络请求，只能等服务器或超时。

现在继续继承主任务的限速、配额和任务身份，只将音轨上下文的控制路径改为自己的 `audio.control`。没有上下文的直接调用也设置该路径。不新增线程、依赖、配置、重试或网络超时。正常 `finish` 仍沿用已有的录制收尾语义。

## 实际证据

新增回归使用真实本地 HTTP 服务：确认音轨清单请求到达后保持服务器阻塞，只回收音轨线程，主任务始终为 `run`。要求服务端释放连接前回收完成，且主任务控制文件保持 `run`。通过消息通道协调先后关系，不用睡眠碰运气；3 秒仅作为失败期限。

在 Windows Sandbox 中，未修复生产逻辑的测试程序退出码 101，回归在 3.02 秒后失败：音轨线程仍等待服务端。释放服务端后才退出。修复后的 HLS 27 项回归全部通过，包括该故障、外置音轨失败、正常 VOD 音视频交错下载与暂停恢复、自动直播识别和时间轴恢复。显式 curl 2 项、WinHTTP 3 项停止和请求回归也通过，共 32 项。本批未重跑上一批全部 636 项，未将旧成绩当本批全量通过。

这是一个已复现的 HLS 卡住原因，不能据此确认用户此前卡死现场就是同一原因，也不能证明指定直播站点的 403 已解决。没有重试此前被审批拒绝的直播录制，没有在宿主运行产品或调用云端。
